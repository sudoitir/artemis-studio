# Artemis Studio

**یک کنسول برای همهٔ کلاسترهای Apache ActiveMQ Artemis که دارید.**

توپولوژی زنده، همهٔ صف‌های همهٔ نودها در یک جدول، مسیر پیام‌ها جلوی چشمتان، عملیات امن روی پیام‌ها و جست‌وجوی پیام‌ها با SQL؛ همه از یک نمونهٔ Studio.

## شروع سریع

Studio و Postgres آن، از روی ایمیج منتشرشده. بروکرهایتان همان‌طور که هستند می‌مانند: آن‌ها را در رابط کاربری ثبت می‌کنید و هیچ‌کدام از این دستورها بروکری راه نمی‌اندازد.

</div>

```bash
base=https://raw.githubusercontent.com/sudoitir/artemis-studio/main/deploy/compose
curl -sO "$base/compose.prod.yaml"
curl -s "$base/.env.example" | sed \
  -e "s|^SECRET_KEY=.*|SECRET_KEY=$(openssl rand -base64 32)|" \
  -e "s|^DB_PASSWORD=.*|DB_PASSWORD=$(openssl rand -hex 24)|" > .env
docker compose -f compose.prod.yaml --env-file .env up -d
docker compose -f compose.prod.yaml logs studio | grep -A4 'Created administrator'
```

<div dir="rtl" align="right">

سپس <http://localhost:8080> را باز کنید و با کاربر `admin` و رمزی که خط آخر چاپ می‌کند وارد شوید. این رمز فقط یک بار نشان داده می‌شود و در اولین ورود، رمز دلخواه خودتان را انتخاب می‌کنید.

</div>

<details>
<summary dir="rtl">از روی کلون مخزن با <code>just</code>، یا یک کانتینر تنها روی Postgres خودتان</summary>

```bash
git clone https://github.com/sudoitir/artemis-studio && cd artemis-studio
just up          # همین استک، قفل‌شده روی آخرین نسخه
```

```bash
docker run -p 8080:8080 \
  -e ARTEMIS_STUDIO_DB_URL=jdbc:postgresql://db:5432/artemis_studio \
  -e ARTEMIS_STUDIO_DB_USER=artemis_studio \
  -e ARTEMIS_STUDIO_DB_PASSWORD=... \
  -e ARTEMIS_STUDIO_SECRET_KEY="$(openssl rand -base64 32)" \
  sudoit1/artemis-studio:dev
```

</details>

<div dir="rtl" align="right">

همهٔ متغیرها، تنظیمی که reverse proxy برای جریان SSE لازم دارد و راه بازیابی اولین ورودِ ازدست‌رفته در [راهنمای پیکربندی](https://sudoitir.github.io/artemis-studio/fa/guide/configuration) آمده است.

## چرا

ساعت سه بامداد است و `ORDERS.DLQ` جایی در کلاستر شما دارد پر می‌شود. کنسولی که همراه Artemis می‌آید هر بار فقط یک بروکر را مدیریت می‌کند و اصلاً از وجود کلاستر خبر ندارد؛ پس برای هر نود یک تب باز می‌کنید، در هر کدام درخت JMX را زیر و رو می‌کنید و attributeها را یکی‌یکی می‌خوانید تا بالاخره پیدایش کنید.

Artemis Studio **کلاستر را واحد همه‌چیز** می‌داند. همهٔ نودهای همهٔ کلاسترها روی یک توپولوژی‌اند و نقش HA هرکدام زنده poll می‌شود. همهٔ صف‌های همهٔ نودها هم در یک جدول‌اند، مرتب‌شده بر اساس عمق صف؛ پس صفی که دنبالش بودید ردیف اول است. یک نمونهٔ Studio برای هر تعداد کلاستری که دارید کافی است و روی همان بروکرهای فعلی‌تان کار می‌کند.

<a href="https://sudoitir.github.io/artemis-studio/fa/"><img src="docs/img/story.webp" width="1600" height="900" alt="داستان ساعت ۰۳:۰۷ با یک هشدار شروع می‌شود: عمق ORDERS.DLQ جایی میان ۸ بروکر در ۲ کلاستر بالا می‌رود. آن را در مرورگرتان بازی کنید."></a>

**[▶ داستان را بازی کنید](https://sudoitir.github.io/artemis-studio/fa/)**: اول خودتان با یک تب برای هر بروکر دنبال صف بگردید، بعد ببینید Studio چطور آن را در یک صفحه پیدا می‌کند.

<div dir="rtl" align="right">

- **توپولوژی**: جفت‌های live/backup و وضعیت replication آن‌ها. نقش HA در هر چرخه از تک‌تک نودها poll می‌شود و هرگز از پیکربندی خوانده نمی‌شود؛ اگر در یک جفت دو نود هم‌زمان live باشند، هشدار split-brain داده می‌شود.
- **[Flow](https://sudoitir.github.io/artemis-studio/guide/flow)**: کدام اپلیکیشن به کدام آدرس پیام می‌فرستد، آن آدرس از مسیر divertها، bridgeها و پرش‌های کلاستر به کدام صف‌ها می‌رسد، و چه کسی با چه نرخی آن‌ها را مصرف می‌کند. مشکلاتی مثل انباشت پیام بدون مصرف‌کننده با کلمات روشن گفته می‌شوند، و از کلاینت‌ها فقط تا وقتی کسی صفحه را نگاه می‌کند نمونه‌برداری می‌شود.
- **[SQL Console](https://sudoitir.github.io/artemis-studio/fa/guide/sql-console)**: Artemis نمی‌تواند بگوید *سفارش ۴۴۷۱ کجا رفت*. تنها فیلتر سمت سرورش JMS selector است: فقط هدرها را می‌بیند و هیچ‌وقت بدنهٔ پیام را نه، آن هم هر بار فقط یک صف روی یک نود. Studio از پسش برمی‌آید:

</div>

```sql
SELECT * FROM "ORDER.*"
WHERE body->>'orderId' = '4471'
LIMIT 50
```

<div dir="rtl" align="right">

زبان کوئری فقط `SELECT` فقط‌خواندنی است و با فهرست ثابتی از ستون‌ها سنجیده می‌شود، پس هیچ کوئری‌ای نمی‌تواند چیزی را تغییر دهد. شرط‌های روی هدر به JMS selector تبدیل می‌شوند و هزینه‌ای ندارند؛ شرط‌های روی بدنه نیاز به پیمایش دارند، و **نوار plan پیش از اجرای کوئری می‌گوید کدام حالت است**. کوئری‌ای که از سقف هزینه بگذرد همراه با برآوردش رد می‌شود، نه اینکه بی‌صدا نتیجه‌اش بریده شود. می‌توانید tail زنده اضافه کنید یا برای یک صف [capture کامل](https://sudoitir.github.io/artemis-studio/fa/guide/message-capture) را روشن کنید: یک کپی با ظرفیت محدود روی خود بروکر که Studio آن را تخلیه می‌کند، تا حتی پیامی که بین دو poll مصرف شده هم قابل پیدا کردن باشد.

- **منابع همهٔ نودها**: صف‌ها، آدرس‌ها، مصرف‌کننده‌ها، نشست‌ها، اتصال‌ها و تولیدکننده‌ها در یک جدول مجازی؛ هر ردیف نشان می‌دهد مال کدام نود است و از طریق SSE به‌روز می‌ماند.
- **عملیات روی پیام**: مرور، ارسال، جابه‌جایی، retry، منقضی‌کردن، حذف و purge. هر فراخوانی تغییردهنده `?dryRun=true` را می‌پذیرد، عملیات گروهی در سمت سرور سقف دارند و نتیجه به تفکیک نود گزارش می‌شود.
- **ردیابی request-reply**: درخواست‌ها در همهٔ آدرس‌ها و نودها به پاسخ‌هایشان وصل می‌شوند و آمار تأخیر و timeout با انتظاراتی که تعریف کرده‌اید سنجیده می‌شود.
- **[پیکربندی بروکر](https://sudoitir.github.io/artemis-studio/fa/guide/broker-configuration)**: address settingها، security settingها، divertها، bridgeها و صف‌هایی را که کلاستر باید داشته باشد تعریف کنید و مسیریابی بینشان را روی یک بوم بچینید. آن‌ها را اول روی یک نود قناری اعمال کنید، در حالی که پیش از هر نوشتنی همهٔ خطرها گفته می‌شود، یا به‌صورت بخشی از `broker.xml` خروجی بگیرید و ببینید هر نود کجا از تعریف فاصله گرفته است. در اولین اجرا، Studio وضعیت فعلی کلاستر را به‌عنوان نسخهٔ ۱ پیشنهاد می‌دهد؛ بی‌اجازهٔ شما چیزی پذیرفته نمی‌شود، و هیچ bridgeای هرگز پذیرفته نمی‌شود، چون بروکر فقط بخشی از آن را گزارش می‌کند.
- **[بازبینی راه‌اندازی](https://sudoitir.github.io/artemis-studio/guide/setup-review)**: پیکربندی HA، کلاسترینگ، ماندگاری و ایمنی پیام در هر کلاستر با اشتباه‌های شناخته‌شده سنجیده می‌شود: یک جفت replication تنها که نمی‌تواند در رأی‌گیری quorum برنده شود، redistribution که روی `-1` مانده، connectorی که `localhost` را اعلام می‌کند، نبودِ آدرس dead-letter. هر یافته شواهدش را به تفکیک نود و اصلاحیهٔ `broker.xml` را همراه دارد، و می‌توان آن را با ذکر دلیل و به‌صورت ثبت‌شده، به‌عنوان ریسکی شناخته‌شده پذیرفت.
- **[ارسال هشدار](https://sudoitir.github.io/artemis-studio/guide/alert-delivery)**: Slack، Microsoft Teams، PagerDuty (incidentها همراه با هشدار باز و بسته می‌شوند)، ایمیل و webhookهای امضاشده؛ هرکدام پیش از ذخیره آزمایش می‌شود و گزارش ارسال می‌گوید چرا یک اعلان نرسیده است.
- **[حاکمیت داده](https://sudoitir.github.io/artemis-studio/guide/data-governance)**: هدرها و propertyهای حساس پوشانده می‌شوند، اطلاعات شخصی (PII) خودکار دسته‌بندی می‌شود و پوشاندنشان به نقش بیننده بستگی دارد.
- **حاکمیت**: احراز هویت در همه‌جا، نقش‌ها و مجوزها در سه سطح سراسری ← محیط ← کلاستر، توکن‌های API، OIDC/SSO اختیاری، و گزارش ممیزی‌ای که هر تغییر و نتیجه‌اش را ثبت می‌کند.
- **[سرور MCP](https://sudoitir.github.io/artemis-studio/fa/guide/mcp)**: همین قابلیت‌ها برای دستیار هوش مصنوعی، با همان مجوزها و همان گزارش ممیزی.
- **[پلاگین‌ها](https://sudoitir.github.io/artemis-studio/guide/plugins)**: فایل `.jar` یک پلاگین را از رابط کاربری نصب کنید؛ با صفحه‌ها، API، ابزارهای دستیار و داده‌های مخصوص خودش. پیش از تأیید، هر کاری که می‌تواند بکند نشان داده می‌شود و جز در صورت نیاز، راه‌اندازی مجدد لازم نیست. به‌روزرسانی‌ها نشان می‌دهند چه چیزی عوض می‌شود و قابل بازگشت‌اند؛ پلاگینی که خطا بدهد هرگز Studio را از کار نمی‌اندازد. برای شروع یک پلاگین از [قالب آماده](examples/plugin-template) استفاده کنید.

## چطور کار می‌کند

چهار قاعده در سراسر محصول برقرار است:

- **از پایه، هوای بروکر را دارد.** خواندن‌ها دسته‌ای است (برای هر نود یک POST به Jolokia، هرگز یکی برای هر صف)، polling لایه‌بندی شده و برای هر نود محدودیت نرخ وجود دارد. Studio هرگز نباید دلیل از پا افتادن یک بروکر باشد.
- **پیش‌فرض، ایمنی است.** هر فراخوانی مخرب را می‌شود اول به‌صورت dry run اجرا کرد، و برای purge و حذف باید نام منبع را تایپ کنید.
- **وضعیت HA از نودها می‌آید، نه از پیکربندی.** اینکه چه کسی live است را فقط نودهای live می‌دانند.
- **صداقت دربارهٔ قابلیت‌ها.** اگر قابلیتی در دسترس نباشد، همین را می‌گوید و دقیقاً همان `broker.xml` لازم برای فعال‌کردنش را نشان می‌دهد. هیچ‌چیز بی‌صدا ناپدید نمی‌شود.

Java 25 · Spring Boot 4.1 · PostgreSQL با Liquibase · React 19 + Vite + Mantine 9 · TanStack Router/Query/Table · React Flow · در درجهٔ اول Jolokia روی HTTP و در درجهٔ دوم کلاینت Core خود Artemis · SSE · یک ایمیج کانتینر. [معماری](https://sudoitir.github.io/artemis-studio/reference/architecture) و [همهٔ تصمیم‌های ثبت‌شده](https://sudoitir.github.io/artemis-studio/reference/adr/) را بخوانید.

## انتشار نسخه‌ها

هر merge که اپلیکیشن را تغییر دهد یک نسخهٔ جدید منتشر می‌کند. شمارهٔ نسخه به شکل CalVer (`YYYY.MM.PATCH`) است و روی Docker Hub سه تگ می‌گیرد: `2026.09.3` (تغییرناپذیر)، `2026.09` (همان ماه) و `dev` (آخرین نسخه). تا اولین نسخهٔ پایدار، تگ `:latest` نداریم. فایل jar قابل‌اجرا همراه `.sha256` به هر نسخه پیوست می‌شود و یادداشت‌های انتشار از پیام‌های commit ساخته می‌شوند ([GitHub Releases](https://github.com/sudoitir/artemis-studio/releases)). API پلاگین (Maven Central) و SDK (npm) همراه نسخه‌هایی منتشر می‌شوند که تغییرشان می‌دهند.

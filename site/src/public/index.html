01 / Flow

Watch the messages move.

Mid-incident, "what's in this queue" isn't really the question. It's who sends here, where does it go, and why is it piling up? Flow draws the whole path for a cluster:

  • Producers, then addresses, then queues, then consumers, with diverts, bridges and the hops between nodes.
  • Dots move along every edge, faster and denser as the path gets busier.
  • Colour only shows up when something is wrong, and the problem is spelled out: no consumer, stalled, not connected.

02 / Safe operations

Fix it without flinching.

At 3 a.m. the dangerous part isn't finding the queue. It's the button you press next.

  • Every destructive call takes ?dryRun=true and answers with the affected count, without doing anything.
  • Purge and delete need the queue's own name typed in to confirm.
  • The audit event is written in the same transaction as the command, before the broker call, so even a crash mid-operation leaves a record.

03 / SQL Console

Ask the question you actually have.

"Where did order 4471 go?" Artemis can't answer that. Its only server-side filter is a JMS selector, which never sees the body and runs against one queue on one node at a time.

  • One query covers every queue in the cluster, including message bodies.
  • It's SELECT-only and parsed to an AST, so no mutation can even be written.
  • The plan shows what each predicate costs before it runs: target, pushdown or scan.

04 / Your brokers

Keep your brokers exactly as they are.

Studio registers the brokers you already run. It doesn't install them, doesn't restart them, and never writes broker.xml.

  • Nothing to rewrite beyond the management endpoints you almost certainly already have on.
  • If a capability is missing, the UI says so and shows the exact snippet that enables it. Nothing just silently disappears.
  • It goes easy on the broker: reads are batched into one Jolokia POST per node, never one per queue, behind a per-node rate limiter.
